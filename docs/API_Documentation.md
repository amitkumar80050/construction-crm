# Attendance API

All endpoints use the CRM API base path `/api` and require a bearer access token. Attendance dates are generated by the server in UTC using `YYYY-MM-DD`; check-in and check-out timestamps are generated by the server.

| Method | Path | Access | Description |
| --- | --- | --- | --- |
| `POST` | `/attendance/checkin` | Any authenticated user | Create today's attendance record and check-in timestamp. A second check-in for the same user and date returns `409`. |
| `POST` | `/attendance/checkout` | Any authenticated user | Record today's check-out. Requires an existing check-in and can be used once. |
| `GET` | `/attendance/my` | Any authenticated user | Return the signed-in user's latest attendance records. |
| `GET` | `/attendance/pending` | Manager or admin | List pending attendance for the manager's teams; admins can see all employees. A user cannot review their own attendance. |
| `PUT` | `/attendance/:id/approve` | Manager or admin | Approve a pending record. Optional JSON body: `{"managerRemarks":"Optional note"}`. |
| `PUT` | `/attendance/:id/reject` | Manager or admin | Reject a pending record. Optional JSON body: `{"reason":"Optional remark"}`. Managers can only review members of their teams. |

Attendance records include `user`, `date`, `checkInTime`, `checkOutTime`, `status`, `managerId`, and `managerRemarks`. `status` is `PENDING`, `APPROVED`, or `REJECTED`. Rejection reasons are also returned in `managerRemarks` (and the legacy `rejectionReason` field).

The legacy `/attendance/mark` and `/attendance/:id/review` routes remain available for existing clients; new clients should use the check-in/check-out and explicit approve/reject routes above.

# Manager Workflow API

Every `/manager` route requires a Manager or Admin token. Managers are restricted to their own teams; Admins have company-wide scope.

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/manager/dashboard` | Return lead totals/stages, call-note counts, scheduled/completed/missed site-visit KPIs, pending attendance, team members, and unassigned/team leads. |
| `POST` | `/manager/distribute` | Auto-distribute unassigned `NEW` leads round-robin. Send `{"leadIds":[...],"assignedTo":"<telecallerId>"}` to manually assign selected leads to one active team Telecaller; omit `assignedTo` for round-robin. |
| `POST` | `/manager/assign-visit` | Schedule an executive visit. Required: `leadId`, `executiveId`, future `scheduledAt`, `address`, `priority` (`LOW`, `MEDIUM`, `HIGH`), and `notes`. The lead must be `SITE_VISIT_PLANNED`; the executive must be on the acting Manager's team. |
| `GET` | `/manager/attendance?period=week` | List team attendance for `today`, `week` (default), or `all`; optional `status` filter. |
| `PUT` | `/manager/attendance/:id` | Legacy review alias accepting `{"status":"APPROVED"|"REJECTED","managerRemarks":"Optional remark"}`. Explicit approve/reject routes under `/attendance/:id/...` are preferred. |

New site visits use `PLANNED`, `DONE`, and `MISSED` statuses; legacy `SCHEDULED`, `COMPLETED`, and `NOT_DONE` records remain readable. Completed visits require an uploaded photo and valid GPS coordinates and advance the lead to `SITE_VISIT_DONE`.

# Notifications API

All endpoints require a bearer access token. Each user can list and mark read only their own notifications. Responses are newest first, paginated, and include a count of all unread notifications for the current user.

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/notifications?limit=20&page=1` | List the current user's notifications; `unread=true` filters to unread entries. The response includes `data`, `unreadCount`, `page`, and `limit`. |
| `PUT` | `/notifications/:id/read` | Mark one of the current user's notifications as read. Returns `404` for another user's notification. |
| `PUT` | `/notifications/read-all` | Mark all of the current user's unread notifications as read. |

New notification events are pushed to the authenticated user's Socket.IO connection using `notification:new`. Current event types include `LEAD_ASSIGNED`, `SITE_VISIT_ASSIGNED`, `SITE_VISIT_COMPLETED`, `SITE_VISIT_NOT_DONE`, `ATTENDANCE_APPROVED`, and `ATTENDANCE_REJECTED`.

# Teams and Users API

All routes require a bearer access token. Role identifiers are the lowercase values stored in `User.role`: `admin`, `manager`, `telecaller`, and `sales executer`. The `User.teamIds` array is the team-membership source used for manager scoping. Assigning a team lead synchronizes that manager's membership automatically.

## Teams

| Method | Path | Access | Description |
| --- | --- | --- | --- |
| `GET` | `/teams` | Any authenticated user | Admins see all teams; other roles see only teams in their own `teamIds`. |
| `POST` | `/teams` | Admin | Create a team. Requires unique `name` and `code`; optional `teamLead` must reference an active Manager. The Manager is linked to `User.teamIds`. |
| `GET` | `/teams/:teamId` | Admin, assigned Manager | Read team details and members. Managers may only read their own team. |
| `PATCH` | `/teams/:teamId` | Admin | Update name, code, department, description, status, or team lead. Manager membership is synchronized when the lead changes. |
| `DELETE` | `/teams/:teamId` | Admin | Delete an empty team. Returns `400` while any user remains assigned. |
| `POST` | `/teams/:teamId/members` | Admin | Assign a Telecaller or Sales Executive to the team. |
| `DELETE` | `/teams/:teamId/members/:userId` | Admin | Remove a team member. A team lead must first be reassigned. |

The admin team screen uses these `/api/teams` routes. Admin-only aliases are also available under `/api/auth/teams` for list, create, update (`PUT /:id`), and delete.

## Users

| Method | Path | Access | Description |
| --- | --- | --- | --- |
| `GET` | `/auth/users` | Admin, Manager | Admins list all non-deleted users. Managers list only their team's Telecallers and Sales Executives. |
| `POST` | `/auth/users` | Admin | Create a user with a supported role and optional team assignment; account verification follows the existing OTP flow. |
| `PUT` | `/auth/users/:id` | Admin; Manager for own-team Telecaller/Sales Executive | Update user information. Manager updates are limited to name, phone, and active status; role, permissions, email, and team membership cannot be changed. |
| `DELETE` | `/auth/users/:id` | Admin | Soft-delete/deactivate a user. |

The canonical admin user-management routes are also under `/api/users`; role and permission changes use their dedicated admin-only endpoints. Managers cannot edit themselves, other Managers, Admins, or users outside their teams. Telecallers and Sales Executives cannot use user-management routes.

# Leads API

All routes require a bearer access token. Role values are `admin`, `manager`, `telecaller`, and `sales executer`. Telecallers and Sales Executives see assigned leads; Managers see leads in their teams; Admins see all leads.

| Method | Path | Access | Description |
| --- | --- | --- | --- |
| `GET` | `/leads?stage=NEW&status=lead` | Any CRM role | List leads within the caller's assignment/team scope; optional stage and status filters. |
| `POST` | `/leads` | Admin, Manager, Telecaller | Create a lead with required name, company, email, and phone. Email or phone duplicates return `409`. Managers/Admins may set a team; Telecaller-created leads are assigned to the caller. |
| `GET` | `/leads/:id` | Scoped user | Return lead details, chronological stage history, and recent notes. |
| `PUT` | `/leads/:id` | Manager or Admin | Reassign to an active Telecaller or Sales Executive. Managers may assign only to members of their own team. |
| `PATCH` | `/leads/:id/stage` | Scoped user, role constrained | Advance one stage at a time with required notes. Follow-up requires a future date. A Sales Executive cannot mark a visit done through this API; completion requires the site-visit photo/GPS workflow. |
| `POST` | `/leads/:id/notes` | Scoped user | Add a required call note. |
| `POST` | `/leads/distribute` | Manager or Admin | Round-robin distribute unassigned `NEW` leads in the selected team to active Telecallers. Managers can only distribute their own teams. |
| `DELETE` | `/clients/:id` | Admin | Delete a lead through the legacy Client alias. |

The allowed next-stage rules are: Telecaller `NEW -> CONNECTED -> INTERESTED -> FOLLOW_UP -> SITE_VISIT_PLANNED`; Sales Executive completes a planned visit through the proof-backed visit endpoint, which advances the lead to `SITE_VISIT_DONE`; Manager/Admin advance `SITE_VISIT_DONE -> QUOTATION -> CONVERTED`. Stage changes require notes and cannot move backwards or skip stages. Imports use `/import/csv` or `/import/excel`, `/import/preview`, and `/import/process`; imports flag duplicates by email or phone and default to skipping them.
